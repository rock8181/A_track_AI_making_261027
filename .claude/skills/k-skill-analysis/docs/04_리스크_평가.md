### 1-2. 로컬 환경에서 관찰된 사실 (저장소 원본 확인 전)

- 현재 세션에 설치된 스킬 목록의 설명에 `k-skill-proxy` 경유 호출을 명시한 스킬이 다수 있다 (예: 국회 의안, 공공데이터 기반 조회, 카카오 지도, 고속버스·시외버스 예매, 산림휴양 예약 등).
- 카카오톡(`kakaotalk-mac`), 카카오 지도(`kakao-map`), 예약류(`heyyumi`, `express-bus-booking`, `intercity-bus-booking`, `foresttrip-vacancy`, `ticket-availability`) 스킬도 설치되어 있다.
- 다만 이 스킬들이 `NomaDamas/k-skill` 저장소에서 왔는지, 설치 버전이 무엇인지는 확인되지 않았다. 저장소 원본 확인이 선행되어야 한다.

### 1-3. 이 문서의 한계

- 저장소 코드, 커밋 이력, LICENSE, SECURITY.md, SKILL.md의 권한 설정은 이 문서 작성 시 열람하지 않았다.
- 따라서 아래 평가표의 "미확인" 항목은 모두 직접 확인이 필요하다. 추측으로 채우지 않았다.

## 3. 주요 리스크 심층 검토

### 3-1. 3인 소규모 기여자 체제

- 근거: Contributors 3 (확인됨).
- 해석: 관리자 1~2인에 의존하는 구조일 가능성이 있다. 이는 추정이며, 커밋 비중을 확인해야 한다.
- 리스크:
  - 관리자 이탈 시 외부 사이트 변경 대응이 멈출 수 있다.
  - 리뷰 인력이 적어 악의적 PR이 병합될 가능성이 상대적으로 높을 수 있다 (추정).
  - 공급망 공격 시 검토자가 적어 탐지가 늦어질 수 있다.
- 완화책:
  - 특정 커밋 해시에 고정(pinning)하고, 업데이트를 수동 검토 후 반영한다.
  - 포크본을 내부 저장소로 가져와 검토된 버전만 사용한다.
  - 최근 3개월 커밋과 머지 권한자를 확인한다.

### 3-2. 프록시(k-skill-proxy) 경유 호출

- 근거: 설치된 스킬 설명에서 `k-skill-proxy` 경유를 명시한 스킬이 다수 확인됨 (1-2 참조). 원본 저장소 기준 확인은 미완료.
- 리스크:
  - 사용자의 조회 내용(주소, 열차 구간, 검색어, 예약 조건)이 프록시 운영자에게 전달된다.
  - 프록시가 API 키를 보관하면 키 유출 시 피해 범위가 넓다.
  - 프록시 장애나 정책 변경 시 여러 스킬이 동시에 동작하지 않을 수 있다.
  - 프록시 응답을 그대로 신뢰하면, 프록시가 변조된 데이터를 줄 경우 판단 오류가 생긴다.
- 완화책:
  - 프록시 소스 공개 여부와 운영 주체를 먼저 확인한다.
  - 민감 입력(주소 상세, 실명, 예약자 정보)은 프록시 경유 스킬에 넣지 않는다.
  - 프록시 없이 직접 호출하는 경로가 있는지 확인하고, 없다면 사용 범위를 제한한다.
  - 프록시 도메인을 방화벽 허용 목록에 명시적으로 등록하고, 그 외 외부 전송은 차단한다.

### 3-3. 카카오톡 및 예약류 스킬

- 근거: 설명의 카카오톡 언급, 설치 스킬 중 카카오톡·예약 계열 존재 (확인됨). 실제 권한 범위는 미확인.
- 리스크:
  - 카카오톡: 로컬 메시지 DB 또는 클라이언트 자동화에 접근하면 대화 내용이 노출될 수 있다.
  - 예약류: 계정 로그인 정보, 결제 수단, 예약자 연락처를 다루면 피해가 직접적이다.
  - 자동 실행 시 사용자가 의도하지 않은 예약·취소·결제가 발생할 수 있다.
  - 예약 사이트의 이용약관 위반(자동화 금지) 리스크가 있다.
- 완화책:
  - 카카오톡 계열 스킬은 메시지 접근 코드 유무를 먼저 확인하고, 없으면 도입 범위에서 제외하는 것을 기본값으로 한다.
  - 예약 스킬은 사용자 승인 없이 확정 단계로 넘어가지 않는지 확인한다. 확정 버튼 직전에 멈추는 구조만 허용한다.
  - 계정 로그인 정보는 환경변수나 평문 파일에 두지 않고, 세션을 직접 입력하는 방식으로 제한한다.
  - 테스트는 실제 계정이 아닌 더미 계정 또는 조회 전용 경로에서만 수행한다.

## 4. 도입 체크리스트

도입 전 아래 항목을 모두 확인하고, 미확인 항목이 남아 있으면 해당 스킬은 보류한다.

### 4-1. 저장소 기본 점검
- [ ] Stars, Forks, Contributors, Issues 수치를 캡처가 아닌 실시간 페이지에서 재확인하고 날짜를 기록했다.
- [ ] 최근 커밋 날짜를 확인했다. 6개월 이상 정체면 보류 또는 위험 등급 상향.
- [ ] 상위 커밋 작성자 비중을 확인했다. 1인 비중이 과반이면 단일 관리자 의존으로 기록.
- [ ] LICENSE 파일을 열어 허용 범위를 기록했다. 없으면 사용하지 않는다.
- [ ] SECURITY.md 존재 여부와 취약점 제보 경로를 확인했다.
- [ ] 고정할 커밋 해시 또는 태그를 정했다.

### 4-2. 코드 점검
- [ ] 키·토큰 스캔(`gitleaks` 등)을 현재 버전과 이력 전체에 실행했다.
- [ ] 의존성 취약점 스캔(`npm audit`, `pip-audit` 등)을 실행했다.
- [ ] 각 사용 예정 스킬의 `SKILL.md`에서 허용 도구와 실행 권한을 확인했다.
- [ ] 설치 스크립트가 전역 설정(PATH, 셸 프로파일, 스케줄러)을 바꾸지 않는지 확인했다.
- [ ] 호출 대상 도메인 목록을 만들고, 목록에 없는 도메인으로의 전송이 없는지 확인했다.

### 4-3. 프록시 점검
- [ ] k-skill-proxy의 소스 공개 여부와 운영 주체를 확인했다.
- [ ] 프록시 요청 로깅 및 보관 정책을 확인했다.
- [ ] 사용할 스킬 목록 중 프록시 경유 스킬을 표시했다.
- [ ] 민감 입력을 프록시로 보내지 않는다는 규칙을 팀에 공유했다.

### 4-4. 개인정보 및 권한 점검
- [ ] 카카오톡 스킬의 메시지 접근 여부를 확인했다. 접근하면 도입을 보류하거나 범위를 제한했다.
- [ ] 예약 스킬의 입력 필드와 결제 경로를 확인했다.
- [ ] 로그 파일 위치와 개인정보 포함 여부를 확인했다.
- [ ] 자동 확정 경로가 없고, 사용자 승인 단계가 있음을 확인했다.
- [ ] API 키와 계정 정보의 저장 위치(평문 여부)를 확인했다.

### 4-5. 운영 점검
- [ ] 샌드박스 또는 별도 계정에서 스킬 1개씩 실행해 동작을 검증했다.
- [ ] 프록시 장애, API 변경 시 실패 방식(조용한 실패 vs 명시적 오류)을 확인했다.
- [ ] 업데이트 시 변경 내역을 검토하는 절차를 정했다.
- [ ] 문제 발생 시 스킬 제거 절차와 키 폐기 절차를 정했다.

### 4-6. 최종 판정 기준
- 4-1, 4-2, 4-4 항목 중 하나라도 미확인 상태이면 해당 스킬은 **도입 보류**.
- 프록시 경유 스킬은 4-3 완료 후에만 도입.
- 카카오톡·예약 스킬은 권한 범위가 확인되고, 승인 단계가 있을 때만 제한적으로 도입.
